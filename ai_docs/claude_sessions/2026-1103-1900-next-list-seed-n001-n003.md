## 3. N-003: namespace-load failures in the Pod Watch picker

### Problem

`loadWatchNamespaces()` (`web/embeds/watch.js`) ended in
`.catch(function(){})`. Worse, the common failure never reached the catch.
`GET /api/namespaces` answers a bad selection with
`503 {"error":"no kubeconfig context available"}`, which `r.json()` parsed
fine. `data.namespaces` was then undefined, so the picker showed "— no
namespaces —", and Start said "Pick a namespace to watch". No cause was shown
anywhere.

### Fix (`web/embeds/watch.js` only)

- New `jsonOrThrow(r)` helper. It rejects non-2xx responses with the server's
  `{"error"}` message, falling back to `HTTP <status>`. `postJSON` now uses it
  too (same behavior as before, just deduplicated).
- On failure:
  - the picker is cleared and shows a disabled "— failed to load namespaces —"
    entry, with the cause in its tooltip;
  - the notice line shows the cause;
  - `nsLoadError` is stored, so `watchStart` repeats the cause instead of
    "Pick a namespace".

  Old options are cleared, not kept: a failure usually follows a context
  change, so stale entries belong to the wrong cluster.
- On success, `nsLoadError` resets and the normal tooltip is restored.

### Verification

- `node --check web/embeds/watch.js` passes.
- Built a throwaway binary and ran it with a nonexistent `KUBECONFIG` and a
  scratch state file on port 8377. Confirmed the 503 + `{"error": ...}` shape
  that the new path parses.
- The rendered failure state has **not** been looked at in a browser or
  KRo.app. That check is raised as N-020.
